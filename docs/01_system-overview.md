# System Overview

## 1. 目的

飲食店のメニュー更新は、店舗・会社・運用代行者によって管理方法が異なる。

例：

- 自社サイトで管理して複数グルメサイトへ転記
- 食べログを正本にして他サービスへ転記
- CSVやスプレッドシートを正本にする
- 店舗ごとにカテゴリ構造が違う
- 外部サイトごとに管理画面DOMが違う

本システムは、このバラバラなメニュー管理を `Common Menu Model` を中心に整理し、Chrome拡張を使って外部サイト管理画面への入力を安全に補助する。

---

## 2. 解決する課題

### 2.1 メニュー更新の二重入力

新商品、価格変更、季節限定商品の終了などを複数サイトへ手入力する必要がある。

### 2.2 店舗ごとの管理方法の違い

同じ飲食チェーンや同じコンサル案件でも、店舗ごとに正本やカテゴリが違う可能性がある。

### 2.3 外部サイト管理画面の変更

食べログ・ホットペッパー・ぐるなび等の管理画面DOMは外部要因で変わる可能性がある。

### 2.4 誤更新時の復旧

メニュー価格やカテゴリを間違って反映した場合、いつ・誰が・何を変更したか追跡でき、過去バージョンに戻せる必要がある。

## 4. 基本ユースケース

### Use Case 1: 自社DBから外部サイトへ反映

```txt
自社DB
↓
Common Menu Model
↓
ホットペッパー管理画面へ自動入力
```

### Use Case 2: 食べログを正本にする

```txt
食べログ管理画面から読み取り
↓
Common Menu Model
↓
ホットペッパー・ぐるなびへ入力補助
```

### Use Case 3: CSVから取り込み

```txt
CSV
↓
Common Menu Model
↓
複数外部サイトへ入力補助
```

### Use Case 4: 季節限定メニュー終了

```txt
sale_end_date到来
↓
非公開候補として差分表示
↓
人間確認
↓
外部サイトへ反映
```

---

## 5. システム境界

### 本システムが担当すること

- メニュー情報の一元管理
- メニュー履歴管理
- 共通形式への変換
- 外部サイトDOM検出
- 入力補助
- DOM差分検知
- 店舗別カテゴリ学習
- 同期ログ保存

### 本システムがMVPでは担当しないこと

- 外部サイトへの完全自動公開
- ログイン認証の自動突破
- CAPTCHA回避
- Cookie保存
- 外部サイトの利用規約を無視した操作
- 生DOM全文の恒久保存

---

## 7. 重要な前提

- 外部サービスの管理画面はいつ変わってもおかしくない
- 店舗ごとにカテゴリや契約プランが違う可能性がある
- 完全自動化よりも安全な半自動化を優先する
- 失敗をゼロにするより、危険時に止まる設計にする
- 更新履歴とログを最重要視する
